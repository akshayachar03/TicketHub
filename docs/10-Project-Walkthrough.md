
# 🚀 TicketHub Project Walkthrough (Interview Perspective)

> **Purpose**
>
> This document explains the TicketHub project exactly the way I would present it during a technical interview. The focus is on the DevOps implementation rather than the application development.

---

# 1. Introduction

Hello, I'd like to walk you through one of my end-to-end DevOps projects called **TicketHub**.

TicketHub is a cloud-native ticket management application that I deployed on Microsoft Azure using modern DevOps practices. While the application itself is built with React, Node.js, Express, and MongoDB Atlas, my primary goal was not application development—it was to design, automate, deploy, monitor, and troubleshoot a complete DevOps workflow.

This project helped me gain practical experience with Docker, Azure Kubernetes Service (AKS), GitHub Actions, Argo CD, Helm, Prometheus, Grafana, Azure Monitor, and Log Analytics.

---

# 2. Project Objective

The objective of this project was to simulate a real-world software delivery pipeline.

Instead of deploying an application manually, I wanted to automate the complete lifecycle—from a developer pushing code to the application running in Kubernetes with monitoring enabled.

The goals were:

- Containerize the application.
- Automate builds using CI.
- Deploy through GitOps.
- Run the application on Kubernetes.
- Monitor both the application and infrastructure.
- Learn Azure-native DevOps services.

---

# 3. Application Overview

The application is a simple ticket management system.

Technology stack:

- React (Frontend)
- Node.js & Express (Backend)
- MongoDB Atlas (Database)

I intentionally kept the application simple because my primary focus was implementing the DevOps lifecycle around it.

---

# 4. High-Level Architecture

The complete flow is:

Developer
→ GitHub Repository
→ GitHub Actions
→ Azure Container Registry
→ Helm
→ Argo CD
→ Azure Kubernetes Service
→ Prometheus
→ Grafana
→ Azure Monitor
→ Log Analytics

The developer only pushes code to GitHub. Everything else is automated.

---

# 5. Docker Implementation

The first thing I did was containerize both the frontend and backend.

I wanted the application to run consistently in every environment without worrying about local dependencies.

I created separate Dockerfiles for the frontend and backend and verified that both images worked correctly before moving to Kubernetes.

Once the images were ready, they became the deployment artifacts used throughout the project.

**Key Takeaway**

The application became portable, reproducible, and ready for cloud deployment.

---

# 6. Azure Container Registry (ACR)

After building the Docker images, I needed a private container registry where Kubernetes could pull them from.

I used Azure Container Registry as the central image repository.

Every new build generated by GitHub Actions is pushed to ACR with the latest image tag.

AKS always pulls images from ACR instead of local Docker images.

**Key Takeaway**

ACR acts as the single source for container images.

---

# 7. Azure Kubernetes Service (AKS)

Next, I provisioned an Azure Kubernetes Service cluster to host the application.

Inside AKS, I deployed:

- Namespace
- Deployments
- Services
- Ingress
- ConfigMaps
- Secrets
- ServiceMonitor

Kubernetes became responsible for scheduling, restarting failed Pods, rolling updates, and service discovery.

**Key Takeaway**

AKS provides a highly available platform for running containerized applications.

---

# 8. Helm

Managing multiple Kubernetes YAML files quickly became difficult.

To simplify deployments, I packaged all Kubernetes resources into a Helm chart.

Helm allowed me to:

- Reuse templates.
- Manage configuration through `values.yaml`.
- Upgrade deployments more easily.
- Keep Kubernetes manifests organized.

**Key Takeaway**

Helm simplified deployment management and versioning.

---

# 9. GitHub Actions (Continuous Integration)

Once the infrastructure was ready, I automated the build process.

Whenever code is pushed to the repository:

1. GitHub Actions starts automatically.
2. The source code is checked out.
3. Docker images are built.
4. Images are pushed to Azure Container Registry.
5. Helm image tags are updated.
6. The updated configuration is committed back to Git.

One important design decision was that GitHub Actions **does not deploy** the application.

Its responsibility ends after producing and publishing deployment artifacts.

**Key Takeaway**

GitHub Actions is responsible for Continuous Integration, not deployment.

---

# 10. GitOps with Argo CD (Continuous Delivery)

For deployment, I adopted a GitOps approach using Argo CD.

Argo CD continuously watches the Git repository.

When GitHub Actions updates the Helm values file, Argo CD detects the change automatically.

It compares the desired state stored in Git with the live state running inside Kubernetes.

If a difference is found, Argo CD synchronizes the cluster automatically.

This means I never need to run `kubectl apply` manually after GitOps is configured.

**Key Takeaway**

Git becomes the single source of truth for deployments.

---

# 11. Kubernetes Deployment Flow

The complete deployment process is:

Developer Pushes Code

↓

GitHub Actions Builds Images

↓

Images Pushed to ACR

↓

Helm Values Updated

↓

Git Repository Updated

↓

Argo CD Detects Change

↓

AKS Synchronizes

↓

Pods Updated

↓

Application Available

This entire process is fully automated.

---

# 12. Monitoring & Observability

Once deployment was automated, the next goal was monitoring.

I implemented two monitoring solutions.

## Application Monitoring

- Prometheus collects application metrics.
- Grafana visualizes those metrics.

## Infrastructure Monitoring

- Azure Monitor collects Azure infrastructure telemetry.
- Log Analytics stores logs and metrics.
- KQL is used to query monitoring data.

This combination provides visibility into both the application and the underlying infrastructure.

**Key Takeaway**

Monitoring should cover both the application and the platform it runs on.

# 13. Challenges I Faced

While implementing the project, I encountered several practical DevOps issues.

Some examples include:

- `/metrics` endpoint returning 404.
- CrashLoopBackOff during deployment.
- Kubernetes Service labels missing.
- ServiceMonitor selector mismatch.
- Prometheus target remaining DOWN.
- Grafana dashboards showing **No Data**.
- Azure Monitor provider registration issue.
- Telemetry delay in Log Analytics.

Each issue helped me better understand how the different DevOps components interact.

# 16. Project Summary

To summarize, TicketHub demonstrates a complete Azure DevOps workflow.

Starting from a developer push, the application is automatically built, stored in Azure Container Registry, deployed to Azure Kubernetes Service through GitOps using Argo CD, and monitored using Prometheus, Grafana, Azure Monitor, and Log Analytics.

The application itself is intentionally simple. The primary value of this project lies in the DevOps practices implemented around it.

This project significantly improved my understanding of CI/CD, Kubernetes, GitOps, cloud infrastructure, monitoring, and real-world troubleshooting, giving me practical experience with the tools commonly used in modern DevOps environments.
